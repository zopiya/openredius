# 12 · 后 MVP 产品与运行模型

## 结论

M0–M7 已完整覆盖“单实例、人工运维”的准入管理主链路：用户、策略、NAS、认证、会话、
CoA、AD 同步、告警和部署均可用。下一阶段的首要目标不是增加更多页面，而是让每次策略
变更可预演、可审批、可回滚，让服务故障可发现、可处置、可证明恢复。

因此后续工作按以下顺序推进：**运行基线 → 变更治理 → 身份与生态集成 → 规模与韧性**。
访客 Portal 已有 `/api/portal/*` 保留命名空间，但不应抢在前述基线之前实施。

## 现状与设计缺口

| 维度 | 已具备 | 仍缺少的闭环 |
|---|---|---|
| 准入控制 | RADIUS 策略编译、802.1X、CoA、终端与 NAS 管理 | 策略变更的影响范围预演、审批、灰度和一键回退 |
| 运营可见性 | dashboard、告警规则、JSON 日志、`/api/health` | 指标、SLO、告警分级/升级、值班和恢复证据 |
| 安全治理 | JWT、三角色 RBAC、审计、Secret 掩码 | SSO/MFA、权限定期复核、break-glass、双人审批 |
| 数据保护 | backup/restore 脚本、14 份保留 | 自动化恢复验证、RPO/RTO 目标、异地副本和演练记录 |
| 集成 | AD 增量同步、预留 webhook UI、预留 portal/metrics 端点 | 受认证的 webhook、工单/SIEM 对接、IdP 联邦 |
| 可用性 | Docker Compose 单实例与健康检查 | 多副本调度、配置发布、FreeRADIUS 池与故障切换 |

这里的“缺少”不等同于缺陷：它们是单实例 MVP 的合理边界；进入生产常态运营后才成为
优先事项。

## 能力路线

### M8 · 运行基线与可观测性（必须先做）

**目标**：建立可量化的服务健康和恢复能力，使告警能够被值班人员行动。

- 实现受网络边界保护的 Prometheus `/api/metrics`；覆盖 API 延迟/错误、认证接受与拒绝、
  CoA 结果、策略编译、AD 同步、任务延迟、数据库连接和 FreeRADIUS 健康。
- 定义第一版 SLO：控制台 API 月可用性、认证成功率、认证日志入库延迟、关键告警确认时限；
  数值由服务负责人根据 NAS 数量和业务时段在实施前确认。
- 为 critical/warning/info 定义通知、确认、升级、关闭与复盘规则；告警事件要记录 owner、
  ack、解决时间和关联事件，而不仅是 read_at。
- 将备份改为“备份 + 定期隔离环境恢复验证”；每次演练产生带恢复点、耗时、校验结果和审批
  人的记录，最终确定 RPO/RTO。
- HTTP E2E 基线已在 v0.1.0 收尾(`bun run e2e:http`,9 页走查 + 深链用例,见 09);M8 将其
  纳入发布门禁并在每次发布时重跑。

**完成信号**：一份月度 SLO 报告、一次成功恢复演练、一次模拟 NAS/数据库故障演练，以及
完整的 HTTP E2E 证据。

### M9 · 策略与配置变更治理（必须先做）

**目标**：把高风险的即时写入改为受控发布，不破坏紧急处置速度。

- 引入 `change_request` / `policy_revision` 概念：草稿、预演、待审批、已排程、执行中、
  已发布、已回滚、已取消均保留不可变审计轨迹。
- 对策略、批量用户操作、NAS Secret/地址、核心 RADIUS 设置提供 diff 与 blast-radius：受影响
  用户、终端、NAS、VLAN/ACL、现有在线会话和预计 CoA 数量。
- 常规变更采用四眼审批；提交者不能审批自身请求。紧急变更可走 break-glass，但必须在时限内
  补充原因、复核人和事后复盘。
- 发布采用编译预检 → 小范围/指定 NAS 灰度 → 健康校验 → 扩大范围；失败时自动停止并支持
  按 revision 回退。所有动作关联 `audit_log` 与告警事件。
- 首版保持单实例和同步数据库事务；异步任务、消息队列和复杂工作流仅在有明确吞吐需求后引入。

**完成信号**：一条策略从草稿到回滚的自动化验收；审批分离职责测试；每次发布可由 revision
重建下发产物。

### M10 · 身份、终端与运营生态集成（高价值，依赖 M8/M9）

**目标**：降低人工账户/终端维护成本，并让安全运营能够消费准入事件。

- 管理员登录对接 OIDC/SAML SSO，优先支持 MFA；本地管理员仅保留受控的 break-glass 账户。
  角色仍以 OpenRedius 内部角色为授权事实，IdP group 仅做映射来源。
- 扩展终端生命周期：登记、所有权校验、例外申请、到期、复核、撤销；对 EDR/MDM/证书源使用
  拉取或 webhook 适配器，保留来源、时间和证据，避免把合规判断硬编码在 RADIUS unlang。
- 将 webhook 从设置页占位变为签名、重试、幂等、投递审计齐全的 outbound event；优先输出
  `auth.reject`、`nas.offline`、`policy.published`、`endpoint.noncompliant` 到 SIEM/工单系统。
- 访客 Portal 仅在有明确的 sponsor、访客身份源、隔离 VLAN 与到期回收责任后立项；其 token、
  自助密码和访问凭据不得与管理后台 JWT 复用。

**完成信号**：IdP 不可用时 break-glass 流程可用；一条端点合规变化能在有签名和可重放保护下
送达外部系统；例外到期会自动撤销或产生升级告警。

### M11 · 多站点与高可用（按规模触发）

**触发条件**：单点故障不可接受、存在多个站点/网络域，或认证与审计量超过单实例容量基线。

- 将 NAS、策略和事件显式归属 `site`/`radius_cluster`；所有查询与授权先限定租户/站点边界。
- FreeRADIUS 使用至少两个无状态节点与 NAS 侧主备；配置与 SQL schema 按版本发布，节点逐个
  drain/reload，不能依赖人工“重启整个容器”。
- 后端可水平扩展前，APScheduler 改为单领导者或外置调度；登录限流、refresh 黑名单、任务锁和
  告警去重移出进程内存。
- 灾备从单机备份扩展到异地副本、恢复演练和明确的降级策略。

**完成信号**：任一后端或 RADIUS 节点失效不导致认证中断；滚动发布和站点级故障演练通过。

## 角色与授权演进

现有 `admin` / `operator` / `auditor` 是 UI/API 权限角色，仍是 M8 的唯一授权模型。运行
职责可以由同一人兼任，但必须在变更记录中可追溯；生产规模下应尽量分离。

| 运行职责 | 现有最小角色 | 可做的事 | 不得单独完成的事 |
|---|---|---|---|
| 服务负责人 | admin | SLO、风险接受、紧急授权、恢复演练结论 | 审批自己提交的常规变更 |
| 准入运营人员 | operator | 用户启停、AD 同步、会话下线、告警初判 | 策略/NAS/系统设置变更、Secret 查看 |
| 网络/RADIUS 管理员 | admin | NAS 生命周期、策略发布执行、RADIUS 故障处理 | 自己的策略请求审批；无工单的破坏性操作 |
| 安全审计员 | auditor | 审计查询、证据导出、权限/变更复核 | 修改任何生产状态 |
| 应急值班人员 | operator + 临时授权 | 按 SOP 处置会话、确认/升级事件 | 常规策略发布；break-glass 后不补审计 |

M9 起新增的是“请求者/审批者/执行者”职责约束，而不是急于新增大量常驻 RBAC 角色。若
需要实现，应以 capability + resource scope（site、NAS 组、策略域）演进，兼容现有三角色。

## 取舍与不做事项

- 不把“多租户 SaaS”作为近期目标；当前模型是单组织内部部署，M11 的 site/cluster 是运营
  隔离而非商业租户。
- 不在 M8 引入 Kafka、Kubernetes 或 service mesh。先以指标、持久化记录和可靠脚本验证需要。
- 不因 UI 中已有 webhook 开关或 API 预留端点而视为已承诺功能；这两者均需各自立项和安全设计。
- 不允许 Portal 绕过 802.1X、隔离 VLAN 或终端生命周期规则。
